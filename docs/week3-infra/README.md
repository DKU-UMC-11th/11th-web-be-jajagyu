# 3주차 인프라 - 장애를 견디는 시스템 만들기

2주차에서 찾은 병목(서버 1대 기준 약 500 RPS에서 꺾임)을 고치고, 같은 조건으로 다시 재서 비교했음. 이어서 부하(CPU/메모리)가 올라갈 때 오토스케일링이 요청을 놓치지 않는지 확인했음.

## 한눈에 보기
| | 2주차 (개선 전) | 3주차 (개선 후) |
|---|---|---|
| 꺾이는 RPS | 약 **500** (서버 1대) | 600 RPS에서도 안 꺾임. 이 측정 도구로 확인 가능한 최대 약 **630 RPS** 이상 |
| 그때 p99 | 600 RPS에서 **2,966ms** | 600 RPS에서 **295ms** (800 RPS 목표에서도 353ms) |
| 그때 에러율 | 600 RPS에서 타임아웃 331건 / 17,559건 = **1.9%** | **0%** (600/800 RPS 모두 실패 0건) |

- 같은 조건 = 서버 1대(t3.small), RDS db.t3.micro, 단계 40초, 시작 전 200 RPS 60초 워밍업, `POST /movie-records`. 원본: `loadtest-0-baseline.json`, `loadtest-2-query2.json`.
- 2주차 원 측정(`../week2-infra/loadtest-before-1node.json`)에서도 600 RPS에서 처리량이 약 502/s에서 멈추고 p99가 3,127ms, 800 RPS에서 타임아웃 247건이었음. 같은 모양이라 개선 전 값으로 다시 쟀음.
- "에러율"은 서버 5xx가 아니라 **타임아웃(클라이언트 관점)** 기준임. 서버의 5xx 비율은 계속 0%였음.

## 1. 병목 개선 (워크북 3장)
2주차에서 읽은 것: DB는 한가한데(`threads_running` 4~6) 앱의 Hikari 풀이 가득 차 요청이 줄을 섰음. 그리고 서버 CPU도 80%대였음.

### 3.1 커넥션 풀 늘리기 (10 → 20, 연결 대기 5초)
- Spring 방식으로 옮겼음: `spring.datasource.hikari.maximum-pool-size`(기본 10), `connection-timeout`(기본 30초 → 5초). 환경 변수 `DB_POOL_SIZE`, `DB_CONN_TIMEOUT`로 열어서 이미지를 다시 만들지 않고 SSM 값만 바꿔 비교했음.
- RDS `max_connections`가 61이라, 서버 3대 × 풀 20 = 60이면 한도에 거의 붙음. 풀을 더 늘리려면 DB 쪽도 같이 봐야 함.

| 목표 RPS | 처리량 | 실패 (타임아웃) | p95 | p99 | 서버 CPU |
|---|---|---|---|---|---|
| 400 | 373/s | 2 | 1,827ms | 2,637ms | 99% |
| 600 | 460/s | 5 | 2,863ms | 3,499ms | 99% |
| 800 | 431/s | 4,782 | 4,918ms | 4,984ms | 100% |

- 새 스택에서는 풀을 늘렸더니 **오히려 나빴음**(개선 전은 400 RPS에서 p95 66ms). 옛 스택에서 같은 변경을 했을 때는 800 목표에서 741/s, 실패 0으로 좋아졌었음(`loadtest-after31-pool20-warm.json`).
- 서버가 이미 CPU 100%라서(앱 컨테이너가 코어를 거의 다 씀, Alloy는 2%) 풀을 늘려도 처리량이 안 늘고, 동시에 도는 트랜잭션만 늘어 서로 CPU를 나눠 쓰며 지연이 커진 것으로 해석했음. 이건 확인한 사실이 아니라 내 해석임. 한계 근처(사용률 약 100%)에서는 작은 차이에도 지연이 크게 흔들려서 같은 설정도 환경에 따라 결과가 달랐음.
- 결론: **풀 확대는 CPU가 병목인 곳에서는 효과가 없고, 효과는 환경에 따라 다르다**고 기록함.

### 3.2 쿼리 5번 → 2번 (`MovieRecordService`)
- 전: 회원 조회 → 평점 중복 확인 → 즐겨찾기 중복 확인 → 평점 저장 → 즐겨찾기 저장 (읽기 3 + 쓰기 2)
- 후: 평점 저장 → 즐겨찾기 저장 (쓰기 2). 
  - 회원 조회: `getReferenceById`는 쿼리 없이 FK 값만 가진 껍데기를 줌. 없는 회원이면 INSERT의 **FK 제약**이 거절함 → 404 `MEMBER404_1`.
  - 중복 확인 2개: `(member_id, movie_id)` **UNIQUE 제약**이 이미 막고 있음 → 거절당하면 409 `RATING409_1`/`FAVORITE409_1`.
  - 제약 이름은 DB마다 달라서(MySQL은 스키마 파일 이름, 테스트용 H2는 자동 생성) 이름 대신 SQLSTATE/에러 코드(1062/23505 중복, 1452/23506 FK)로 구분했음.
- 안전한지 확인: 예전과 같은 응답이 나가는지 `MovieRecordApiTest` 4개로 검증함(저장 201, 평점 중복 409, 즐겨찾기만 중복 409 + 평점 롤백, 없는 회원 404). 전체 테스트 19개 통과.
- 주의: 읽기 쿼리를 지워도 되는 이유는 DB 제약이 같은 일을 하기 때문임. 제약이 없는 스키마였다면 쓰면 안 되는 최적화임.

| 목표 RPS | 처리량 | 실패 | p95 | p99 | 서버 CPU |
|---|---|---|---|---|---|
| 400 | 399.5/s | 0 | 52ms | 430ms | 45% |
| 600 | 594.9/s | 0 | 46ms | 295ms | 55% |
| 800 | 628.2/s | 0 | 65ms | 353ms | 60% |

- 같은 400 RPS에서 CPU가 **98% → 45%**로 줄었고, 600 RPS 타임아웃 331건이 0건이 됐음. 요청 하나가 쓰는 CPU/왕복이 줄어든 게 가장 확실한 개선이었음.
- 800 목표에서 처리량이 약 628/s인 것은 서버가 아니라 **내 PC(발사기) 한계**임. 클라이언트 드롭이 6,846건이고, 도구 코드에도 500 RPS 이하만 신뢰한다고 적혀 있음. 그래서 "안 꺾였다"가 아니라 "이 도구로는 약 630 RPS까지 꺾임이 안 보였다"로 적었음.

### 애플리케이션 단에서 처리량을 더 늘릴 방안 (미션)
1. **트랜잭션 안 왕복 수 줄이기** (적용함): 처리 가능 RPS ≈ 커넥션 수 ÷ (왕복 수 × 왕복 시간). 이번엔 왕복을 줄여서 CPU까지 같이 줄었음.
2. **커넥션을 오래 쥐지 않기**: 트랜잭션 범위를 필요한 저장 구간으로 좁히고, 외부 호출을 트랜잭션 밖으로 빼는 방법. (이번엔 외부 호출이 없어서 적용 안 함)
3. **풀 크기는 DB 한도와 함께 정하기**: 서버 수 × 풀 ≤ `max_connections`(61). 지금은 서버 3대 × 20 = 60.
4. **풀 대기 시간을 짧게(5초)**: 쌓인 요청이 30초씩 붙들리지 않고 빨리 실패해서 연쇄를 막음. (적용함)
5. **쓰기 두 번을 한 번으로 합치기 / 비동기 처리**: 즐겨찾기 저장을 분리하거나 배치로 모으는 방법. 응답 일관성 요구를 따져 봐야 해서 적용하지 않았음.

## 2. 오토스케일링 (워크북 3.3)
설정(`aws-autoscaling-check.txt`): CPU 평균 60% 기준, 메모리 70% 기준(CloudWatch Agent의 `mem_used_percent`), 최대 3대, 워밍업 120초, 헬스체크 ELB(유예 180초).
- 메모리는 EC2가 기본으로 보내지 않아서 에이전트를 `userdata`에 추가하고 인스턴스 역할에 `CloudWatchAgentServerPolicy`를 붙였음.
- 기본 모니터링은 5분 간격이라 알람 반응이 15분 넘게 걸려서 **상세 모니터링(1분)**을 켰음.
- 시험 방법: 서버 1대에서 시작해 일정한 요청(300 RPS 14분 / 메모리는 200 RPS 13분)을 계속 보내면서, 서버 안에서 CPU 부하(`yes` 프로세스) 또는 메모리 600MB 점유(python)를 걸었음. 30초마다 서버 수, 타겟 헬스, 알람 상태, 평균 CPU/메모리를 기록했음(`autoscaling-*-timeline.txt`, 시간은 UTC).

| 시험 | 서버 수 변화 | 보낸 요청 | 실패 | 비고 |
|---|---|---|---|---|
| CPU 부하, slow start 없음 | 1 → 3 | 242,337 | **869** (0.36%) | 새 서버가 투입된 약 60초 구간(+330~390초)에 857건 집중 |
| CPU 부하, **ALB slow start 120초** | 1 → 3 | 235,316 | **0** | 느린 요청(>1초) 1,066건은 있었음 |
| 메모리 부하 (평균 71%) | 1 → 3 | 150,673 | **0** | 메모리 알람 → 스케일 아웃, 부하 해제 후 50%대로 내려옴 |

- **스케일 아웃은 동작**했음. CPU 평균이 약 86~90%로 올라가고 약 4.5분 뒤 알람이 울려 2대, 이어서 3대가 됐으며 CPU 평균이 36~38%로 내려왔음.
- **"실패 없이"는 처음엔 안 됐음**: 새 서버는 JVM이 안 데워진 상태로 ALB가 요청의 절반을 바로 보내서, 첫 요청들이 5초 타임아웃에 걸렸음. 헬스체크 통과 시각과 실패 구간이 일치함(`autoscaling-cpu-failures-by-30s.txt`).
- **ALB slow start(120초)**로 새 서버에 트래픽을 서서히 늘리게 했더니 같은 시험에서 실패 0건이 됐음(`autoscaling-cpu-slowstart-failures-by-30s.txt`). 워크북에는 없는 내용이라 내가 추가한 것임.
- 알람 상태의 열 순서는 시험마다 달라 보임(CPU/메모리 알람의 출력 순서가 고정이 아님). 첫 시험은 CPU, 마지막 시험은 메모리 알람이 울렸음.
- 한계: 부하를 서버 안에서 걸어서 한 서버만 포화시킨 시나리오임. 여러 서버가 동시에 포화되거나 DB가 병목인 경우는 확인하지 못했음. 또 스케일 아웃 판단까지 약 4~5분이 걸려서 순간 폭증에는 못 따라감(그 구간은 slow start/타임아웃으로만 버팀).

### /health 의 성격 (워크북 3.3.4 참고)
- 우리 `/health`는 DB를 조회하지 않고 "ok"만 돌려줌. 그래서 풀이 말라도 `/health`가 죽지 않아 ASG가 멀쩡한 앱을 교체하는 일은 없음. 반대로 DB가 끊겨도 헬스체크는 통과함(liveness는 되고 readiness는 아님). 둘을 나누는 것은 하지 않았음.

## 핵심 키워드 (~했음)
- **병목(bottleneck)**: 가장 먼저 포화되는 자원이 전체 처리량을 정한다고 이해했음. 이번엔 풀이 아니라 CPU였고, 한 곳을 고치면 병목이 옮겨갈 수 있음.
- **커넥션 풀과 왕복 수**: 처리 가능 RPS ≈ 커넥션 수 ÷ (왕복 수 × 왕복 시간). 풀을 늘리는 것보다 왕복을 줄이는 게 더 확실했음.
- **FK/UNIQUE 제약으로 읽기 대체**: DB 제약이 이미 같은 검증을 하면 읽기 쿼리를 지울 수 있지만, 제약이 없으면 못 씀.
- **target tracking 오토스케일링**: 지표(CPU/메모리)를 목표값에 유지하도록 서버 수를 조정함. 목표를 높게 잡으면 터진 뒤에야 늘고, 낮게 잡으면 평소에도 서버가 많음.
- **워밍업과 slow start**: 새 서버를 바로 100% 투입하면 JVM이 안 데워져서 실패함. ASG 워밍업은 "아직 안 뜬 서버를 세지 않게"이고, ALB slow start는 "트래픽을 서서히 늘리게"임.
- **blameless 원칙**: 스택 충돌도 "누가 건드렸다"가 아니라 "이름이 겹쳐도 막는 장치가 없었다"로 정리했음.

## 후기
- 가장 크게 배운 것은 **측정값을 그대로 믿으면 안 된다**는 점이었음. 같은 설정인데 스택에 따라 결과가 반대로 나왔고, 원인(CPU 포화, 측정 도구 한계, 워밍업)을 하나씩 찾아가며 어디까지가 확인한 사실이고 어디부터가 해석인지 구분해서 적었음.
- 오토스케일링이 "동작한다"와 "요청을 안 놓친다"는 다른 문제였음. slow start 하나로 실패가 869건에서 0건이 되는 것을 보고, 서버를 늘리는 속도보다 **새 서버를 어떻게 받아 주느냐**가 중요하다는 것을 알았음.
- 아쉬운 점: 부하 발사기가 집 PC라 600 RPS 넘는 구간은 확인하지 못했음. 다음엔 발사기를 같은 리전의 서버에서 돌려 보고 싶음.
- 선택 미션(포스트모템)은 하지 않았음.
